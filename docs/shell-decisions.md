# 셸·페인 설계 결정 (참고문서)

> 페이지 레이아웃 셸을 어떤 기준으로 나누는지에 대한 결정과 그 근거. CLAUDE.md의 요약 블록이 규칙이고, 이 문서는 "왜 그렇게 정했는지"를 담는다. 확정일: 2026-07-02.

---

## 배경 — 왜 이 문서가 필요한가

Phase 2.6에서 상세뷰 구조를 마스터-디테일(좌 리스트 / 우 상세 swap)로 구현하면서, 데스크탑에서 상세 콘텐츠가 좌·우 양쪽에 동시에 뜨는 문제가 있었다. 원인을 추적해보니 **버그가 아니라 패턴 오적용**이었다. 하나의 셸(마스터-디테일)을 모든 페이지에 씌우려다 보니, 성격이 다른 페이지에서 좌우 역할이 무너진 것.

결론: 페이지는 성격에 따라 셸이 다르다. 3패턴으로 나눈다.

---

## 패턴 1 — 콘텐츠 페이지

**정의**: 세로 스크롤 레이아웃. 필요한 구간에만 내부 2단 섹션을 쓴다. 셸 차원의 좌 리스트/우 상세 2패널이 아니다.

**언제**: 소개·인사말·개요처럼 **섹션이 소수·고정**인 페이지. 기관소개(소개및인사말), 연수안내 소개부 등.

**근거**: 마스터-디테일 스왑은 "좌측 리스트 자체가 훑어볼 콘텐츠일 때(항목이 많을 때)"만 성립한다. 섹션이 2~3개뿐인 페이지에 스왑을 씌우면 좌측이 비어 보이고, 비는 게 싫어 좌측을 채우면 우측과 중복된다. 중복은 이 오적용의 증상이다.

**참고 (나인브릿지 셸)**: 포팅해온 나인브릿지 사이트의 원래 구조가 이 패턴이다. 좌측은 실제 콘텐츠(제목·인트로·카드·섹션)로 꽉 채우고, 우측은 대표/브랜드 표현 패널(로고·핵심 메시지·CTA) 또는 요약 역할. 우측이 좌측의 복사본이 아니라 **역할이 다른** 것이 핵심. CONNECT 페이지처럼 한 페이지 안에서 연혁/인증을 2단으로, 문의 폼을 하단에 두는 식으로 "내부 2단 섹션"을 쓴다.

**모바일**: 두 컬럼이 세로로 스택된다. vaul 모달 아님.

---

## 패턴 2 — 마스터-디테일

**정의**: 좌 = 리스트, 우 = 선택 항목 상세(swap). URL이 선택 상태의 단일 진실원천.

**언제**: **항목이 여러 개인 브라우징 리스트**에만. 게시판(공지사항/FAQ), 마이페이지 신청목록.

**페인 역할 (breakpoint별 배타 — 반드시 강제)**:
- 데스크탑: L = 리스트 전용, R = 상세 전용. 같은 콘텐츠가 양쪽에 동시에 뜨면 안 된다. vaul OFF.
- 모바일: L = 전체 리스트, 상세 = vaul 바텀시트 모달 전용. R 페인 없음.

**주의 (알려진 리스크)**: Intercepting Routes의 intercept-state F5 fallback, 딥링크 직접 진입 시 `router.back()`이 갈 곳 없는 history 엣지 케이스는 명시적으로 검증할 것.

**제약**: `MasterDetail.tsx`(Phase 2a)는 재작성 금지.

---

## 패턴 3 — 폼

**신청 폼 (연수신청)**: 모바일 우선 풀폼. 이유 — 신청은 폰 기반 OTP·무로그인 구조라 교사·학부모가 폰으로 신청하는 게 핵심 전환 경로. 데스크탑 전용으로 미루면 안 된다. 데스크탑에서는 우측에 실시간 합계·신청 요약을 sticky 패널로 두는 옵션(= 패턴 1의 좌 콘텐츠/우 요약 구조와 동일 계열).

**부수 폼 (문의·증명요청 등)**: 데스크탑 우선 + 모바일 quick-action 카드 허용. 나인브릿지 CONNECT처럼 모바일에선 전화/카톡/이메일 quick-action + "상세 문의는 데스크탑에서" 처리 가능. ※ 신청 폼에는 이 방식을 적용하지 말 것.

**모바일**: 세로 스택. vaul 모달 아님.

---

## vaul 사용 규칙

vaul 바텀시트 모달은 **패턴 2(마스터-디테일)에서만** 쓴다. 패턴 1·3은 모바일에서 컬럼이 세로로 스택될 뿐 모달을 띄우지 않는다. vaul 기본 비주얼 디테일은 후속 UI 폴리시 트랙으로 이연.
